# Synthesising a subject in Entail

An extract says what a model does. This guide is about the next step: writing a new
program for a subject, informed by that extract, that turns a request into a useful
answer. It records what was done for Python on Qwen 3.5 0.8B, what each step needed,
and what a system that does this without a person would have to supply.

The result is `scripts/entail/subjects/python.synthetic.entail.txt`, generated by
`scripts/entail/synthesise_python.py`. It reads a request in a comment and writes the
line of code that answers it:

```python
# sum the even numbers
result = sum([n for n in numbers if n % 2 == 0])
```

It covers a small slice of Python. It knows a set of operations over three variables,
and is silent about everything else.

## Why not compile the extract

The first idea was to tidy the raw extract and load it back. That can't give useful
output, and the reason decides the design.

Every lane of the raw extract depends only on the previous token and the current one,
so its 1.8 million lines fold exactly into a table of 15,925 decisions. On unseen
third-party code that table agrees with the model on 15.4% of tokens, against 9.9%
for always saying a newline. It has real content, but all of it is a guess at the
next token.

Mathematics works as a law because one exists: the digits fix the answer. A language
has no such law. What is useful depends on what was asked, so a program has to carry
three things: what the request means, what follows from it, and how to write the
result. The extract supplies some of the first and none of the second.

## The shape of the program

| Section | Job | Where it comes from |
|---|---|---|
| Reading | What each token of a request is | The model, the extract, the documentation |
| Gathering | The request line, seen from the `=` | Written by hand |
| Derivation | What the concepts mean together, and whether they make sense | Written by hand |
| Spelling | The plan as a sequence of output tokens | Written by hand |
| Writing | The tokens, one at a time | Written by hand |

Derivation is the part that makes it more than a lookup. `sum the even numbers`
becomes a source, a filter and an aggregate, and those decide the code. The same rules
refuse `sum the words in text`, because a sum needs numbers. That is the link from
request to reasoning to output.

## The steps

### 1. Extract

```bash
amql-cli entail decompile <container> --corpus <dir> --out <dir>
```

The raw extract is the vocabulary to work from. See
[entail-optimisation.md](entail-optimisation.md).

### 2. Fold it

```bash
python scripts/entail/fold_raw.py <raw> <holdout.jsonl> <folded.json>
```

This reduces the extract to the table above and checks that it scores the same as the
extract, so that a claim about the table is a claim about the extract.

### 3. Name the concepts

`scripts/entail/subjects/python.anchors.json` lists the operations the program will
know, such as `reverse`, `sum`, `longest` and `even`. **This is written by hand.** It
decides the program's reach.

### 4. Associate words with concepts

```bash
python scripts/entail/associate.py <raw> <anchors.json> <associations.json>
```

Cosine similarity over idf-weighted neuron vectors, plus words from the documentation.
This groups similar tokens but says nothing about direction: `highest` sits next to
`shortest`, and `sum` has no neighbours at all. Treat it as the weakest source.

### 5. Ask the model what each word means

```bash
python scripts/entail/probe_words.py cases <raw> <associations.json> a.jsonl "the WORD of numbers"
```

```bash
python scripts/entail/probe_words.py cases <raw> <associations.json> b.jsonl "get the WORD of the numbers"
```

```bash
amql-cli --cpu entail eval <container> --tokenizer <dir> --cases a.jsonl --batch 16 --report a.json
```

```bash
amql-cli --cpu entail eval <container> --tokenizer <dir> --cases b.jsonl --batch 16 --report b.json
```

```bash
python scripts/entail/probe_words.py read a.json b.json words.json
```

Each word goes into a request, and the operation in the reply is what the word asks
for. This was the best source by far, giving `lowest`, `smallest` and `total`, which
neurons could not. It needs care, as the first result below shows.

### 6. Write the requests before the lexicon

```bash
python scripts/entail/python_requests.py write requests.jsonl
```

Each request carries a reference expression, and a reply is scored by running both on
real inputs. A reply is useful if it computes the right thing, whatever its spelling.
Keep requests in Python's own words, requests in other words, and requests with no
meaning, where the right reply is no claim at all.

### 7. Generate, graft and score

```bash
python scripts/entail/synthesise_python.py <associations.json> words.json <tokenizer-dir> <out.entail.txt>
```

```bash
amql-cli entail graft <out.entail.txt> --host <checkpoint> --out graft --context 32768
```

```bash
amql-cli encode graft --out graft.container
```

```bash
amql-cli --cpu entail eval graft.container --tokenizer <dir> --cases requests.jsonl --batch 16 --report graft.json
```

```bash
python scripts/entail/python_requests.py score requests.jsonl graft.json --base base.json
```

Run grafts on the CPU: the GPU path rounds the weights. With `--base`, a first line
equal to the base model's counts as the host's answer, so "program spoke" means the
program changed the answer. Where both would write the same line, the two can't be
told apart from the reply.

### 8. Test on requests nobody has tuned against

```bash
python scripts/entail/python_requests.py write fresh.jsonl --fresh
```

Any set you have looked at failures on stops being a test. Write a new one once the
program is finished, score it once, and change nothing because of it. If you do fix
something it reveals, that set is spent, and the next measure needs a new one.

## Results

Qwen 3.5 0.8B. The direct baseline has the same prompt as the graft, and the chat
baseline is the model asked by instruction. Replies were run on real inputs.

| Requests | Direct | Chat | Graft |
|---|---|---|---|
| Plain, 28 | 15 | 11 | 28 |
| Paraphrased, 24 | 9 | 9 | 18 |
| **Unseen, 26** | **14** | **10** | **20** |

The unseen row is the one to quote. The filler words were chosen after seeing
paraphrases fail, and the paraphrases were written after seeing the extract's word
lists, so 18 of 24 is flattering.

What matters is what the program changed against the base model:

| Requests | Answers changed | Fixed | Broken | Re-spelled, still right |
|---|---|---|---|---|
| Plain | 15 | 13 | 0 | 2 |
| Paraphrased | 9 | 9 | 0 | 0 |
| Unseen | 8 | 7 | 1 | 0 |

The one it broke is `items in reverse order`. The base model wrote `items[::-1]`, and
the program wrote `sorted(items, reverse=True)`: it read `order` as a sort and
`reverse` as that sort's direction. That is an error of understanding, since it knew
every word. It is left unfixed so that the unseen figures stay honest.

The other 5 unseen misses are the host's, after the program stayed silent. One shows a
vocabulary trap: in `the smallest positive number` the singular `number` maps to
`count`, because that is what the model wrote for it, so the request has no source.

On requests with no meaning the program stayed silent on all 8, but silence hands the
request back to the host, which answered 4 of them wrongly. The score there is no
better than the base model's. Silence protects the program's own record and does not
yet protect the user.

The program is 6,781 statements, 13,254 neurons and 56 heads, 23 layers deep. Loss on
prose moved from 3.55195 to 3.55207 nats per token.

## What was learned

**A comparison is only as fair as its prompt.** The first baseline had no variables
defined, so the base model scored 1 of 28. Given the same context as the graft it
scores 15. Anything less overstates the program.

**Partial understanding is worse than none.** `add up the even numbers` first produced
a filter with no sum, a confident wrong answer. So the program is closed-world: any
word it cannot place stops it. This is why `arrange numbers in order` falls to the
host even though `numbers` and `order` are known.

**Replies are not equal evidence.** The first probe gave 443 words to `first`, because
the prompt's example indexes a list and the model copies that shape when it doesn't
understand. Word frequency exposed it. A call such as `max(numbers)` is a decision, so
one template is enough if no other names a different call. A bare index is weak, and
needs every template and the whole reply. Check any probe for a default answer before
using its output.

**The lexicon is limited by the extract.** `largest`, `duplicates` and `arrange` were
never probed, because the extract has no entry for them. A probe should take candidates
from the documentation and a word list as well.

**Tokens need checking at the edges.** `\n\n` is one token, so a blank line didn't
count as a line end until it was flagged, and an earlier line's `numbers` could have
leaked into the request.

**Score only what you mean to score.** Replies run on past the answer, and the host
drifts onto later lines that the program then answers. Comparing whole replies made
the program appear to speak on 20 unseen requests when it had changed 8, and blamed it
for an error of the host's. Compare the first line.

**Probing is slow unless cases run together.** Two passes over 2,487 words took just
over 4 hours one at a time. `--batch` answers several cases at once, 4 to 5 times faster on 96
cases, and levels off around 8 to 16 sessions.

## What is hand-written today

Be clear about this when describing the result:

- The concepts and the filler words.
- The derivation: which combinations make sense and what code they become.
- The spelling of each operation.
- The sign patterns that map a reply to a concept.

The machine-derived part is the vocabulary: 134 words from the model, 41 from the
documentation and 8 from the extract, beside 27 concept names. The program demonstrates
the architecture. It doesn't show that reasoning can be derived from a model.

## What a system needs

1. **A subject definition** in place of `python.anchors.json`: operations, their
   arguments and their types, taken from the documentation.
2. **Derivation from types.** Most rules here say that an operation needs a kind of
   input and gives a kind of output. Stated once per operation, a generator could
   derive what composes and what is refused. This is the largest gap.
3. **A wider probe**, with candidate words from outside the extract, several templates,
   and a check for default replies.
4. **Sentence structure.** The program treats a request as a bag of words, which is how
   `reverse order` became a sort. Which word governs which needs at least simple grammar
   in the Reading and Derivation sections.
5. **An answer for silence.** When the program can't place a request, it needs a way to
   say so, or the host answers anyway.
6. **A fresh test set per round,** generated independently of whoever or whatever
   wrote the program, and scored once. This fits the gate in
   [entail-optimisation.md](entail-optimisation.md), with held-out requests in place of
   held-out rows.
